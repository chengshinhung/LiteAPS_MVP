# Feature Specification: LiteAPS 排程模組 PoC 系統

**Feature Branch**: `001-scheduling-poc`  
**Created**: 2026-01-02  
**Status**: Draft  
**Input**: User description: "我要製作 LiteAPS 的小排程模組的PoC 系統"

## 概述

本 PoC（概念驗證）系統目標是建立一個高擬真度的互動網頁原型，用於向高階主管與利害關係人展示 LiteAPS 排程系統的願景與使用者體驗。系統採用「前端模擬」策略，所有運算結果為預先設定的資料，透過視覺效果模擬 AI 排程運算過程。

## Clarifications

### Session 2026-01-03

- Q: 關於系統的回應性能目標，首頁載入時間的期望為何？ → A: 首頁必須在 3 秒內完成載入（快）
- Q: 關於工單資料模型的時間單位，甘特圖 X 軸的時間粒度為何？ → A: 小時（例如：08:00-15:00）
- Q: 關於前端技術框架選擇，開發技術堆疊為何？ → A: React + Vite + TypeScript
- Q: 關於甘特圖的視覺化函式庫選擇，用於實現互動式甘特圖的技術方案為何？ → A: react-google-charts（Google Charts Timeline）
- Q: 關於預設示範資料的工單數量規模，系統內建的模擬資料集大小為何？ → A: 10-15 筆工單（中等規模）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 進入系統首頁並感受專業介面 (Priority: P1)

作為一位高階主管，我進入 LiteAPS 系統首頁時，能夠看到一個簡潔專業的 Dashboard 介面，與傳統 ERP 系統形成明顯對比，讓我對系統產生信任感與興趣。

**Why this priority**: 首頁是使用者的第一印象，直接影響主管對系統的評價與是否願意繼續了解產品。這是爭取資源的關鍵第一步。

**Independent Test**: 可透過載入首頁後觀察介面風格、佈局是否現代化、專業感來驗證，不依賴其他功能。

**Acceptance Scenarios**:

1. **Given** 使用者首次進入系統, **When** 頁面載入完成, **Then** 顯示具有左側導航欄與頂部標題列的現代化 Dashboard 介面
2. **Given** Dashboard 已載入, **When** 使用者觀察介面, **Then** 應能看到儀表板、排程模擬、資源管理等導航項目
3. **Given** 導航欄已顯示, **When** 使用者點擊「排程模擬」, **Then** 系統導航至排程模擬頁面

---

### User Story 2 - 匯入工單 CSV 檔案 (Priority: P1)

作為生管人員，我希望能夠上傳 CSV 格式的工單資料檔案，系統能立即回饋解析結果，讓我確認資料已成功載入。

**Why this priority**: 資料匯入是排程流程的起點，必須讓使用者感受到系統能處理他們的資料格式，建立可行性信任。

**Independent Test**: 可透過選取任意 CSV 檔案後觀察系統是否顯示成功回饋來驗證。

**Acceptance Scenarios**:

1. **Given** 使用者在排程模擬頁面, **When** 點擊「匯入排程工單」按鈕, **Then** 顯示檔案選擇器
2. **Given** 檔案選擇器已開啟, **When** 使用者選取一個 CSV 檔案, **Then** 系統顯示「解析成功：讀取 150 筆工單」的成功提示
3. **Given** 檔案上傳成功, **When** 提示消失後, **Then** 「執行 AI 模擬」按鈕變為可點擊狀態

---

### User Story 3 - 執行 AI 排程模擬並查看進度 (Priority: P1)

作為演示觀眾，我希望在按下「執行 AI 模擬」後，能看到具有進度回饋的運算過程動畫，製造出系統正在進行複雜運算的專業印象。

**Why this priority**: 這是「黑盒子魔法」的核心體驗，用於製造期待感並展示系統的專業性，是說服主管的關鍵時刻。

**Independent Test**: 可透過點擊模擬按鈕後觀察進度動畫與文字變化來驗證。

**Acceptance Scenarios**:

1. **Given** 使用者已上傳 CSV 檔案, **When** 點擊「執行 AI 模擬」按鈕, **Then** 按鈕進入 Loading 狀態且畫面顯示進度指示器
2. **Given** 模擬運算中, **When** 經過約 0.8 秒, **Then** 提示文字輪播切換（如：正在載入機台參數 → 正在偵測交期衝突 → 正在進行啟發式演算法優化）
3. **Given** 模擬運算中, **When** 等待約 2-3 秒後, **Then** 進度動畫結束並自動顯示排程結果

---

### User Story 4 - 查看互動式甘特圖結果 (Priority: P1)

作為高階主管，我希望在 AI 模擬完成後，能看到一個視覺化的甘特圖，清楚展示各機台的排程安排，包含不同類型工單的區別（正常單與急單）。

**Why this priority**: 甘特圖是最終成果的具象化展現，是證明系統價值的核心產出，直接回答「這個系統能做什麼」。

**Independent Test**: 可透過觀察甘特圖是否正確顯示機台、時間軸、工單區塊來驗證。

**Acceptance Scenarios**:

1. **Given** AI 模擬已完成, **When** 結果頁面顯示, **Then** 呈現互動式甘特圖，Y 軸顯示機台名稱，X 軸顯示時間
2. **Given** 甘特圖已顯示, **When** 使用者觀察圖表, **Then** 能看到不同顏色區分的工單（藍色=正常單、紅色=急單、綠色=其他產品）
3. **Given** 甘特圖已顯示, **When** 滑鼠移至某工單區塊上方, **Then** 顯示 Tooltip 包含工單詳情（工單號、產品、時間區間）

---

### User Story 5 - 完成 3 分鐘標準展示流程 (Priority: P2)

作為產品展示者，我希望能在 3 分鐘內完成完整的「上傳 → 等待 → 結果」展示流程，順暢且無技術問題地向主管展示系統能力。

**Why this priority**: 這是整合性的使用者旅程，確保各個獨立功能能串接成完整體驗，但優先級略低於單一功能的正確性。

**Independent Test**: 可透過實際執行完整流程並計時來驗證。

**Acceptance Scenarios**:

1. **Given** 展示者從首頁開始, **When** 依序執行：進入排程模擬 → 上傳 CSV → 執行模擬 → 查看結果, **Then** 整個流程可在 3 分鐘內完成
2. **Given** 展示流程進行中, **When** 任一步驟執行, **Then** 無錯誤訊息或頁面崩潰發生
3. **Given** 系統部署於 GitHub Pages, **When** 使用者重新整理頁面, **Then** 頁面正常載入不出現 404 錯誤

---

### Edge Cases

- 使用者選取非 CSV 格式檔案時，系統仍顯示成功訊息（PoC 階段不實際解析）
- 使用者在模擬運算中重新整理頁面時，回到初始狀態重新開始
- 使用者連續點擊「執行 AI 模擬」按鈕時，按鈕應在 Loading 期間被禁用
- 網路離線時，靜態頁面仍可正常運作（因為不需要後端連線）

## Requirements *(mandatory)*

### Functional Requirements

#### 介面框架

- **FR-001**: 系統必須提供響應式佈局，包含左側導航欄（Sidebar）與頂部標題列（Header）
- **FR-002**: 導航欄必須顯示三個項目：儀表板（Dashboard）、排程模擬（Simulation）、資源管理（Resources）
- **FR-003**: 僅「排程模擬」項目可點擊並導航，其餘項目作為展示裝飾

#### 資料匯入模擬

- **FR-004**: 系統必須提供 CSV 檔案上傳介面元件
- **FR-005**: 當使用者選取檔案後，系統必須立即顯示成功狀態，不實際上傳至伺服器
- **FR-006**: 上傳成功後必須顯示提示訊息「解析成功：讀取 150 筆工單」

#### 運算過程模擬

- **FR-007**: 系統必須提供顯眼的「開始排程最佳化」行動按鈕
- **FR-008**: 點擊模擬按鈕後，系統必須顯示 Loading 狀態並鎖定按鈕
- **FR-009**: 模擬運算期間必須顯示進度指示器（讀取圈或進度條）
- **FR-010**: 模擬運算期間必須每隔約 0.8 秒輪播動態提示文字
- **FR-011**: 模擬運算總時長為 2-3 秒

#### 視覺化結果

- **FR-012**: 系統必須顯示互動式甘特圖，Y 軸為機台、X 軸為時間（以小時為單位，格式如 08:00-15:00）
- **FR-013**: 甘特圖必須從本地預設資料載入工單排程（預設資料集包含 10-15 筆工單，分布於 3 台機台）
- **FR-014**: 不同類型工單必須以不同顏色區分（正常單=藍色、急單=紅色）
- **FR-015**: 滑鼠懸停工單區塊時必須顯示 Tooltip，包含工單詳情（工單號、產品名稱、開始/結束時間）

#### 部署要求

- **FR-016**: 系統必須能部署於 GitHub Pages 靜態網頁託管平台
- **FR-017**: 系統路由必須支援頁面重新整理不產生 404 錯誤

#### 技術堆疊

- **FR-018**: 系統必須使用 React 18+ 作為前端框架
- **FR-019**: 系統必須使用 Vite 作為建構工具
- **FR-020**: 系統必須使用 TypeScript 進行開發，確保類型安全
- **FR-021**: 專案必須包含 tsconfig.json 設定檔，啟用嚴格模式（strict mode）
- **FR-022**: 甘特圖視覺化必須使用 react-google-charts 函式庫（Google Charts Timeline 類型）

### Non-Functional Requirements

#### 效能

- **NFR-001**: 首頁初次載入時間必須在 3 秒內完成（包含所有靜態資源與框架初始化）
- **NFR-002**: 頁面互動回應時間（如按鈕點擊回饋）必須在 100 毫秒內
- **NFR-003**: 甘特圖渲染時間不得超過 1 秒（針對預設資料集規模）

#### 相容性

- **NFR-004**: 系統必須支援現代瀏覽器（Chrome 90+、Edge 90+、Firefox 88+）

### Key Entities

- **工單 (Work Order)**: 代表一筆排程任務，包含以下屬性：
  - 工單號 (Order ID): 唯一識別碼
  - 產品名稱 (Product Name): 生產品項
  - 機台 (Machine): 指派的生產設備
  - 開始時間 (Start Time): 格式為 HH:MM（24 小時制，例如 08:00）
  - 結束時間 (End Time): 格式為 HH:MM（24 小時制，例如 15:00）
  - 類型 (Type): 正常單或急單
- **機台 (Machine)**: 代表一個生產資源，作為甘特圖 Y 軸的分類依據，如 Machine A、B、C
- **排程結果 (Schedule Result)**: 代表模擬運算後的輸出，包含多筆工單在各機台上的時間配置（以小時為時間粒度）

## Assumptions

- 本 PoC 不包含真實後端邏輯與資料庫，所有資料為前端預設
- CSV 檔案上傳為模擬行為，不實際解析檔案內容
- 預設資料設計為「看起來有衝突被 AI 修正」的示範場景，包含 10-15 筆工單分布於 3 台機台
- 預設資料中應包含不同類型工單（正常單與急單）以展示顏色區分效果
- 目標使用者為內部高階主管與潛在利害關係人，非最終使用者
- 系統僅需支援現代瀏覽器（Chrome、Edge、Firefox）
- 開發技術堆疊：React + Vite + TypeScript
- 使用 TypeScript 進行類型安全開發，提升程式碼可維護性
- 甘特圖使用 react-google-charts（Google Charts Timeline），無授權成本且功能滿足 PoC 需求

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 展示者能在 3 分鐘內完成從首頁到甘特圖結果的完整展示流程
- **SC-002**: 首次進入系統的使用者能在 10 秒內理解如何開始操作（找到上傳按鈕）
- **SC-003**: 系統在 GitHub Pages 上穩定運行，頁面重新整理成功率達 100%
- **SC-004**: 觀看展示的主管中，80% 認為介面比傳統 ERP 系統更現代化（主觀評估）
- **SC-005**: 從點擊「執行 AI 模擬」到顯示甘特圖結果的時間控制在 2-3 秒內
- **SC-006**: 甘特圖能清楚呈現 3 台機台與 10-15 筆工單的排程視覺化，展示工單分布與潛在衝突優化效果
